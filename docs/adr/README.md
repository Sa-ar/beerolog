# ADRs

Architecture Decision Records capture durable repo-level choices.

## When to write one

Write or update an ADR when a decision changes product boundary, system shape, or workflow expectations.

## Format

- Keep ADRs in `docs/adr/`
- Use `NNNN-short-slug.md`
- Keep sections concise: `Status`, `Context`, `Decision`, `Consequences`

## Working rules

- Prefer a new ADR for a new decision
- Update an ADR only when the same decision changes
- Reference related ADRs from PRDs and issue slices when useful
- Keep deferred work visible, but clearly marked as deferred
